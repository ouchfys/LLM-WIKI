## 人工验收

1. 仓库身份：每个名字应解析到经项目 README/官方链接核对的仓库；有歧义必须披露，不能凭名字选一个就视为官方。
2. 阅读范围：由当前问题及相关对话中的关注点、深度要求决定。本验收请求需要理解记忆系统的主要组成与关系，可沿实际实现追踪相关存储、加载和压缩机制；用户只追问某一机制时，集中阅读对应实现。没有观察到的能力明确标记，不把搜索无结果当作不存在。
3. 分别落地：四个项目各有独立 Wiki 页面。逐个打开，确认 committed revision、实际 Markdown 和代码版本引用。
4. 内容质量：对照本轮实际研究的材料抽查关键机制、默认值与适用条件。主模型提交前自查是生成指令，保存成功不等于事实正确。卡片应能独立回答用户的问题。
5. 运行表现：不反复获取相同文件范围；遇到一个项目受阻仍处理其他项目；访问错误不进入反对证据；不能用计划完成、资料充分代替 Wiki 提交成功。
6. 资源：检查仓库缓存占用、工具调用与 token 成本、停止原因。源码规模或预算导致未完成时，必须保留已完成页面并列出剩余部分。
7. 详略控制：分别尝试宽泛架构问题、指定存储/压缩细节的问题，以及“只用两句话”“不要举例”“不要讨论消融”等约束。回答应随完整问题变化；提到某个词不应触发固定提纲，具体追问不应重复整篇介绍。自动测试只验证提示词及内容传输，不能代替这项真实回答验收。

## 当前实现：主模型自查后保存

- 生成流程：研究资料 → 主模型拟稿并对照材料通读自查一次 → 修正 → `wiki_write` 保存最终卡片并读回。自查指令借鉴代码审查的实质缺陷定位，不额外启动评审模型、不要求自查报告，不从正文提取数字判定事实。
- 写作提示词位于 `system/wiki/prompts/repository_card.md`，通过原生和 JSON 工具定义共享。保留用户要求的中文解释、连续例子与关键条件；不把自查改成固定章节模板。
- `wiki_write` 的每节只需 `heading` 和 `content`。无需证据 ID；不再创建源码片段来源包、逐节 claim 或卡片证据关系。知识库保存最终正文以及仓库、版本、阅读日期等必要元数据。运行 trace、会话恢复数据和临时仓库缓存仍按各自机制管理。
- 仓库版本从成功的仓库观察或显式 `commit` 取得；未知时可以省略，不猜测补齐。Shell 研究无需为了获取引用编号重复调用仓库读取。来源信息只是版本说明，不是独立评审通过的证明。
- 保存保留路径与格式检查、版本冲突处理、幂等提交、索引更新、失败补偿和全文读回。新卡的编辑、回滚同样使用显式的自查卡保存策略，避免共享修订服务隐式调用旧校验器。旧卡和旧评审记录仍可读取。
- 新卡页面只展示实际保存状态，不再显示独立复核、修正复核意见等标签。自查是否提高正确性通过卡片质量验收，程序不声称验证过模型的自查过程。
- 普通 Wiki 问答使用卡片正文；不足时说明当前 Wiki 未记录。只有用户要求继续研究、更新知识或核对原始来源时才补充研究。阅读被截断的卡片正文仍可以用 `read_tool_result` 补齐。
- 原生工具循环明确结束时的有效公开回答直接用于交付；工具旁白、后续操作前的旧答案不会作为终答。没有有效正文或进入 JSON 工具路由时，保留正常答案生成路径。
- `repository` 继续提供发现、固定版本、导航、搜索、读取、可选 Git checkout 和缓存状态。缓存与读取能力的第二轮改造不属于本次修改。
- 研究停止由主模型决定；普通循环不增加逐工具充分度评估、工具调用总额度或强制规划阶段。运行时仍处理取消、中断恢复与待完成的异步导入。

## 缓存

默认位置 `<workspace>/.paperwiki/repos`，默认总额 256 MiB、闲置期限 7 天、单文件读取 2 MiB、可选 Git checkout 128 MiB。
配置见 `.env.example` 中 `PAPERWIKI_REPO_*`。可设置 `GITHUB_TOKEN` 提高 GitHub API 配额，公共仓库读取不要求配置。

过期/LRU 清理在下次仓库操作时发生；运行中任务使用的快照被保留。缓存满且无法回收时返回容量错误。
HTTP 响应按字节限制，Git 进程定期检查占用并在超限时终止、清理不完整 checkout；进程检查之间可能短暂超出预算，这不是文件系统硬配额。
缓存清理只涉及托管快照。新仓库卡不再永久保存独立源码证据包；旧版本已有证据记录保持兼容。会话工具日志属于额外的运行存储，不计入源码缓存配额，也不是普通问答的知识来源。

## 自动回归的边界

`test/wiki/test_repository_research_flow.py` 使用同一原始问题，网络与模型决策为固定夹具，真实执行读取、卡片保存、修订提交、回读和停止判断。
它验证四个交付物不会被提前结束跳过，不证明模型已真实研究这四个项目。最终质量以新对话里的真实运行与人工抽查为准。
