# PaperWiki：把研究结果变成可持续使用的知识库

**FastAPI · Vue 3 · SQLite · Markdown · 模型工具调用**

PaperWiki 是面向个人论文阅读与公开代码仓库研究的智能体。用户提出问题后，模型自行选择资料与工具；研究结果写成中文知识卡片，后续问答优先读取卡片。目标是让一次研究留下可以继续使用、修改和追溯版本的知识。

> 本文以当前代码为准，更新于 **2026-09-28**。旧复盘描述当时的实现，不代表今天仍启用那些机制。性能数据来自已归档的四仓库实验，**早于最后一次工具精简**，不是当前提交重新跑出的成绩。

## 1. 面试时怎样讲

### 项目解决什么问题

论文阅读和代码研究会产生很多临时答案，但这些答案很难持续维护。我把研究结果保存成知识卡片，让后续问答直接使用经过整理的知识。核心困难是：**原始资料压缩成卡片时容易丢失条件，长任务又容易重复检索、盲目重试和中断丢进度。**

### 我实现了什么

我实现了一个单智能体执行循环：模型决定下一步，程序执行工具、保存调用与结果，再把结果交回模型。模型可以一次提出多项独立读取，程序按依赖组织执行；写入按顺序处理，具体读取能否并发还取决于工具内部实现。论文有专门的解析与入库流程，仓库研究支持定位版本、按文件读取和必要时检出源码。

写仓库卡片时，主模型先对完整草稿自查一次，再提交保存；后续回答以卡片为依据。程序负责格式、版本和保存结果等可以确定检查的事项，语义是否忠实仍需要模型判断。

### 我怎样迭代

我保留失败运行记录，核对工具参数、真实返回、模型用量和最终文件。例如，曾发现数字校验把列表编号和提交哈希误当实验数值；另一次，评审模型把输出额度全部用于思考，程序却把“没有完成评审”当成“证据不支持”。这些错误让主模型不断改写和重试。

后续取消了普通研究的逐工具充分度评估、仓库卡片的独立循环评审和固定检索次数上限，补全原始工具消息、错误反馈和保存回读。最后又精简工具，把 arXiv 的搜索、查详情、入库和查状态合并成一个入口。

### 已经证明什么，还有什么没证明

同一道四仓库研究题，最新归档实验完成 4/4 张卡片，用时约 9 分 19 秒；上一轮约 19 分钟。按同一组历史价格折算，费用从约 2.90 元降至 1.10 元。WorkBuddy 原测试约 27 分 36 秒、1.77 元，但关键事实抽查评分仍领先我们一些。

**这是一个具体任务上的工程改进证据，不能推广为所有研究任务都更快、更便宜或更准确。** 最后一次工具合并已通过定向测试，尚未重跑完整对照实验。

## 2. 从用户请求到答案的完整链路

### 2.1 普通知识问答

```text
用户提问
  → 模型读取问题、相关对话和知识目录
  → 按需打开知识卡片
  → 根据卡片回答；卡片没有记载的内容明确说明
```

普通问答不要求每次回到原论文，也不强制先创建研究计划。用户要求查原文、更新知识或开展新研究时，模型再调用相关工具。

### 2.2 多步研究与 Deep Research 的关系

**PaperWiki 的多步研究由自己的单智能体循环实现，没有把 Jina DeepSearch、LangChain Open Deep Research 或外部 Deep Research 服务接成默认引擎。** DeepSeek 是调用的模型；DeepSeek Harness 是研究对象与设计参考；Deep Research 指多步搜索、阅读、综合和产出的研究方式。

```text
用户问题 → 主模型按需分解任务 → 调用工具 → 保存并返回结果
                         ↑                   ↓
                         └── 继续研究或调整方法 ┘
资料足够 → 拟稿并通读自查一次 → 保存 Wiki 并读回 → 汇报完成项与未知项
```

曾尝试在每次检索后加入独立的证据评估、研究账本和无增益停止规则；这些机制增加了调用，也发生了误判。当前旧协议开关已关闭，代码仍保留作历史兼容。普通问答与复杂研究使用同一个循环：**主模型决定搜什么、研究是否充分；程序负责执行、记录、恢复和提交正确性。**

任务分解不要求写计划文件，也没有默认的“主管—多个研究者”架构；并发工具只是同时执行独立调用。当前没有固定研究调用次数上限，仍保留单次超时、上下文容量、存储限制和用户停止能力。研究四个项目时，主模型应逐篇核对保存回执，并如实说明未完成项。论文入库另走下述专门流程。

实现见 [主循环](system/wiki/wiki_chat.py) 与 [当前验收范围](docs/design/REPOSITORY_RESEARCH_ACCEPTANCE.md)。

### 2.3 论文入库有自己的处理链路

```text
用户给论文名字 / arXiv ID / 链接
  → 名字不明确时搜索候选，核对标题、作者与摘要
  → 提交论文入库，取得任务编号
  → 优先解析 arXiv HTML
  → HTML 不可用或结构质量不足时尝试 MinerU
  → MinerU 不可用或失败时降级到 PyMuPDF
  → 提炼论文知识、检查证据、判断与已有知识的关系
  → 按审批策略保存或生成修改提案
  → 查询任务状态，打开生成的知识卡片
```

HTML 的质量检查关注标题、正文长度、段落和章节结构等，不是论文结论正确性的判断。MinerU 使用外部解析服务，本项目负责提交、轮询、下载和转换结果；没有自行训练文档解析模型。降级解析可能损失复杂公式和表格结构。

**两条写入路径要区分：**仓库研究的 `wiki_write` 使用主模型一次自查；论文入库仍有专门的提炼、评审与合并流程。不能把“取消仓库卡片独立评审”说成整个项目没有论文评审。

## 3. 当前开放的七个工具

工具调用的意思是：模型输出工具名称和结构化参数，由 Python 校验并执行，结果作为工具消息交回模型。模型不会仅凭输出一段命令就自动完成执行。

当前能力概览如下；需要查看参数格式时，直接阅读 [工具定义](system/wiki/agent_tools.py)。

| 工具名称 | 中文作用 | 什么时候使用 |
|---|---|---|
| `local_shell` | 执行命令 | 文件处理、公开网页/API 访问、本地代码搜索和验证 |
| `repository` | 研究 GitHub 仓库 | 查候选仓库、固定版本、定位和读取源码、可选检出 |
| `wiki_write` | 保存仓库知识卡片 | 完稿并自查后提交，返回保存与读回结果 |
| `wiki_open` | 打开知识卡片 | 普通知识问答、读取已写入内容 |
| `evidence_lookup` | 查询保留的原文片段 | 明确要求回查论文等旧卡片来源时 |
| `read_tool_result` | 读取已保存的大结果 | 补读被省略的内容，不重复执行原工具 |
| `arxiv` | 搜索与导入论文 | 搜索、查元数据、入库、查询入库状态 |

当前模型没有独立的 `web_search`、`web_fetch` 工具。相关底层服务仍可能被后台维护功能使用，不代表模型能直接调用。网页查询可以通过命令访问搜索服务或公开 API，具体能力受网络和目标网站限制。

## 4. 知识压缩为什么会失真，怎样改善

原文写“启用某个插件后可以保存长期记忆”，卡片压缩成“系统自动保存长期记忆”，就丢掉了生效条件。原文给出一个可配置参数，卡片写成“产品默认值”，也是失真。流畅、简短、有引用都不能单独证明正确。

当前仓库卡片在提交前要求主模型通读完整草稿一次，重点找：

1. 原文没有支持的事实、因果或保证。
2. 被丢掉的版本、开关、适用条件和例外。
3. 中文转述改变的否定、先后顺序、数量关系。
4. 用户明确问到、却没有回答的核心问题。
5. 正文、公式和例子之间的矛盾。

发现具体问题直接修改；证据不够就缩小结论范围或写明未知。不额外产出评审报告，不以“必须找出问题”为目标，不反复润色到无限循环。见 [完整写作与自查提示词](system/wiki/prompts/repository_card.md)。

这借鉴了代码审查的“指出有依据、可定位、有实际影响的问题”，但没有再启动独立评审智能体。自查能够改善质量，**不能保证主模型发现自己的全部错误**。未来问答依赖卡片，所以必要条件应留在卡片正文里，不能指望以后每次回查原文补救。

论文知识更新仍会召回相关结论，由模型判断补充、冲突或替代关系，再由程序校验结构、来源归属和合法写入范围。审批方式受策略控制；不能据此声称所有命令都无法绕开审批修改文件。

## 5. 运行记录、恢复与上下文管理

### 5.1 模型与程序怎样分工

| 模型负责 | 程序负责 |
|---|---|
| 判断问题需要哪些资料 | 提供工具定义，校验参数与执行结果 |
| 根据观察选择下一步 | 保存调用编号、原始参数、输出和状态 |
| 调整搜索词、改正错误命令 | 执行并发分组和依赖屏障 |
| 判断内容是否足以回答 | 返回错误，不把执行失败解释为事实不成立 |
| 生成并自查卡片 | 写入、版本冲突检查和保存回读 |
| 说明完成项与未知项 | 记录运行结束、失败、暂停或恢复信息 |

原生工具协议保留调用与结果的对应关系；必要时使用 JSON 路由回退。不能在重组上下文时只留下“文件内容”，却丢掉它来自哪条命令、哪个路径。

### 5.2 并发不是“所有读取永远一起执行”

调度层允许最多三个独立读工具同时运行，结果按模型原始调用顺序汇总。但实际能否并发还受工具内部实现影响：当前仓库工具用同一把锁保护整个操作，网络读取和检出也会排队，不能宣称所有仓库读取都并发。写操作和存在依赖的操作形成执行边界。例如，先发现论文编号，再提交入库，不能把两个步骤同时执行。

单次写调用串行，不代表后台所有入库任务只能一个一个跑；后台任务有独立的工作线程配置。`repository` 的缓存写入属于工具内部管理行为，不能把“研究只读”理解为磁盘绝不发生写入。

### 5.3 旧介绍里的几个名词是什么意思

| 名词 | 在本项目里的实际含义 | 不能夸大的地方 |
|---|---|---|
| 状态机 | 记录任务正在执行、等待、完成、失败等状态，并约束迁移 | 回合结束不等于用户所有要求都已完成 |
| 检查点 | 保存请求、调用与已返回结果，让恢复时重建上下文 | 不恢复 Python 调用栈，模型下一步可能变化 |
| 执行租约 | 给一个执行者暂时的任务持有权 | 用于减少多个执行者同时接管 |
| 心跳 | 执行者定期续约，表明仍在工作 | 不证明业务产生了有效进展 |
| 幂等提交 | 同一导入调用或相同已提交内容尽量复用已有结果 | 不能保证任意 Shell 命令自动只执行一次 |

浏览器断开与主动停止是不同事件。服务重启后，可依据持久记录恢复执行；对于执行已开始、结果却未记录的写操作，需要确认实际效果，不能盲目重放。见 [会话恢复](system/agent_runtime/chat_recovery.py)。

### 5.4 完整记录与模型上下文分开

- 完整工具结果保存到 SQLite。大结果交给模型时提供预览、结果编号与补读方式。
- 上下文按 token 预算组织，不是把数据库所有历史无限塞给模型。
- 默认压缩触发配置为窗口的 80%，近期保留配置为窗口的 16%；实际保留量还受其他上下文和摘要预算限制。
- 旧历史生成摘要，近期交互按顺序保留，并保护工具调用与结果配对。
- 普通长工具预览可保留头尾并标明省略，完整结果仍可回读；知识卡片正文有专门的处理路径。
- 压缩摘要帮助继续当前任务，不自动等于可靠的跨会话长期知识。

这些预算保护单次模型请求容量，不是重新加入研究调用次数额度。

### 5.5 代码目录与数据目录分开

默认数据根目录为用户主目录下的 `.paperwiki`。设置 `PAPERWIKI_HOME` 可以改到测试目录，指定目录本身就是数据根，不再额外套一层。

```text
~/.paperwiki/
├── sessions/       会话数据库、任务与工具结果
├── wiki/           生成的 Markdown 知识
├── sources/        论文原件与解析材料
├── memory/         已有项目记忆和兼容数据
├── cache/repos/    仓库缓存
├── tmp/            按会话使用的临时文件
├── projects/       用户明确要求的项目产物
├── archives/       归档的实验与复盘
└── logs/           运行日志
```

目录按需使用，不要求每次对话都创建一个计划文件夹。命令的默认工作目录放在会话临时目录，但显式绝对路径仍可以写到其他位置；这是一条存储约定，不是权限隔离。

## 6. 从失败记录归纳智能体设计问题

这些运行记录反映了几类可以迁移到其他智能体项目的设计问题。同一次失败可能同时涉及上下文、决策和错误恢复；按问题分类，更容易解释修改为什么有效。

| 智能体设计问题 | 本项目中的具体表现 | 根因与设计调整 |
|---|---|---|
| **决策与停止判断**：何时继续、何时交付 | 简单定义题反复查证；一个仓库两轮没有进展，就结束整个四项目任务；固定额度导致只交付 2/4 | 把局部停滞当成全局任务结束，或机械地用调用次数代表研究进度。撤掉逐工具充分度门槛与固定研究额度，主模型按用户目标判断，逐项确认交付、保留未知；程序处理明确的取消与运行故障 |
| **观察与上下文管理**：模型是否看到了正确的信息 | Shell 结果重组时丢失命令与路径，评估器把代码归错文件，模型重读已读内容 | 工具输出失去来源和调用关系，再聪明的模型也可能判断错。保留调用编号、参数、原始返回；完整结果入库，大内容可按编号补读，复用已有观察 |
| **错误反馈与恢复**：重试能否修到真正的问题 | 只返回笼统拒绝，主模型盲改整篇；评审没有输出，被记录为“证据不支持”；GitHub 限流造成资料缺口 | 混淆访问失败、评审未完成和内容错误。保留具体输出与执行状态，让模型针对原因换方法；一个项目受阻时继续其他交付，不能用访问失败推断功能不存在 |
| **知识压缩与校验边界**：如何保持事实含义 | 列表编号、提交哈希被当事实数字，8 次写入遭拒；最新卡片仍会遗漏默认条件 | 代码缺少语义上下文，机械匹配无法判断一句话的含义。仓库卡片改为主模型对完整草稿自查一次，程序检查格式、版本和保存；默认行为、条件与例子是否准确仍需质量抽查 |
| **调用编排与资源分配**：哪些步骤值得再问模型 | 12 次充分度评估消耗约 27.6 万 token；8 次评审把每次 16000 输出 token 全用于思考，没有正文 | 在主循环外叠加评估与重试，会重复传材料、重复推理；评审输出配置又没有适应思考消耗。移除普通研究逐步评估和仓库卡片独立循环评审；独立读调用可批量并发，写入与依赖步骤有序执行 |
| **工具职责与接口设计**：什么应由模型选择 | 默认工具仍混有历史计划、记忆更新和多个论文入口；另有未进入主链路的 MCP 包装 | 将内部管理动作暴露为模型动作，增加协议维护和选择负担。保留七个当前工具，把 arXiv 四种动作统一；自动记录由程序负责，补读结果才由模型按需调用 |

### 从修复失败到衡量效果

9 月 26 日交付 **1/4**；9 月 27 日先出现 **0/4**，后续评审阶段交付 **2/4**；到 9 月 28 日两轮均交付 **4/4**，用时从约 **19 分钟**降到 **9 分 19 秒**。这说明交付能力改善，但各轮改动不止一个，不能把所有收益归到某一条规则。

这期间也撤回过错误方向：为了阻止无限研究加入的充分度评估，反而因为观察失真产生误判和额外开销。当前的分工是：**语义判断交给掌握上下文的模型，可以确定检查的执行与存储事项交给程序。** 主模型仍可能遗漏信息；减少机械门槛后，需要用真实产物验证质量，不能把“保存成功”当成“知识正确”。

## 7. 与 WorkBuddy 的对比

### 7.1 比较任务

两边研究 DeepSeek Harness、Codex CLI、Pi、Hermes 的记忆系统，分别生成四篇知识卡片，回答：

1. 对话保存在哪里，模型每次读取哪部分，近期内容按消息条数还是 token 选择？
2. 上下文压缩如何触发、提示词要求保留什么、摘要落盘还是进入上下文？
3. 长期记忆维护什么？
4. 用一个连续例子串起机制。

WorkBuddy 也获得了写作参考。两边系统提示、工具与服务配置不完全相同，部分仓库版本不同；WorkBuddy 没有随每次 PaperWiki 改动重跑。因此这是**任务案例对照**，不是严格控制变量的框架排名。

### 7.4 产物质量

人工按事实准确性 40、问题覆盖 30、可读性 20、追溯 10 分抽查关键结论：

| 卡片 | 最新归档 PaperWiki | WorkBuddy |
|---|---:|---:|
| Pi | 87 | 90 |
| DeepSeek Harness | 82 | 86 |
| Codex CLI | 77 | 82 |
| Hermes | 74 | 82 |
| **平均** | **80** | **85** |

这是带主观判断的编辑评分，不是全量事实准确率，也不是独立评测榜单。WorkBuddy 产物同样有错误，不能把它当标准答案。

PaperWiki 的四篇可见正文约 1.13 万字符，WorkBuddy 约 2.46 万字符。我们的结构更统一、适合快速查阅，但也漏掉了应当回答的内容：

- 把底层组件“路径参数必填”当成产品没有默认会话目录，没有继续追基础配置。
- 把某条压缩路径的规则泛化到整个产品，遗漏不同供应商或模式的条件。
- 介绍长期记忆时只给文件名，没充分解释默认位置、维护内容和启用条件。
- 最终跨项目汇总新增了卡片未证明的统一执行顺序。

所以当前结论是：**交付效率明显改善，事实覆盖仍需继续提高。** 正确方向是追清默认装配、调用者与条件，并在一次完稿自查中发现具体问题；尚无证据支持重新增加每步评估或多轮评审。

## 8. 为什么这次更快、更便宜：原始记录里的具体原因

逐轮检查原始记录后，差异可以落到三个问题：**命令花了多久、研究怎样安排、文章写完后又做了多少工作。** 下面比较的是这一次运行，不是两款产品的能力上限。

### 8.1 时间主要花在哪里？

| 时间花在哪 | WorkBuddy | PaperWiki |
|---|---:|---:|
| 等模型返回 | 约 7 分 41 秒 | 约 5 分 49 秒 |
| 执行工具，重叠时间只算一次 | 约 18 分 48 秒 | 约 3 分 7 秒 |
| 其他准备与间隔 | 约 1 分 7 秒 | 约 23 秒 |
| **总计** | **27 分 36 秒** | **9 分 19 秒** |

两边相差约 18 分钟，其中约 **86% 的时间差在工具执行**。所以，之前只说“我们请求模型的次数少，因此更快”并不充分。这次首先要看 WorkBuddy 执行了哪些耗时命令。

### 8.2 WorkBuddy 的几条命令确实等了很久

| 实际做了什么 | 耗时 |
|---|---:|
| 用一条循环命令，按顺序浅克隆四个仓库 | 5 分 21 秒 |
| 在 Codex 的大目录里递归搜索调用点 | 1 分 8 秒 |
| 在 DeepSeek Harness 仓库递归搜索会话路径 | 1 分 34 秒 |
| 在 Hermes 仓库递归搜索摘要提示词 | 1 分 40 秒 |

**仅这四条命令就花了 9 分 43 秒。** 后三条是本地搜索，不是网络请求。搜索结果包含历史笔记、评测、插件和网站文件，说明实际查找范围很宽；在输出里过滤无关路径，也不等于搜索时没有遍历那些目录。

PaperWiki 这次主要按目录和指定文件范围读取，没有成功克隆四个完整工作目录。因此，本轮避免了一部分下载和大范围扫描。但不能说克隆不好：大量跨文件研究可能更适合本地检索，WorkBuddy 的广泛查找也找到了一些我们漏掉的核心信息。

记录能定位“哪条命令慢”，没有记录磁盘、进程启动等内部耗时，不能继续猜成某个操作系统或搜索程序本身有问题。

### 8.3 WorkBuddy 写完以后，还继续补查和修改了 24 轮

它的 110 次模型请求实际分为：

| 阶段 | 模型轮次 | 大约时间 |
|---|---:|---:|
| 找仓库、准备与克隆 | 4 | 6 分 8 秒 |
| 阅读源码、写前补查 | 67 | 15 分 36 秒 |
| 建目录，写四篇卡片和四份证据文件 | 9 | 2 分 51 秒 |
| 写完后补查、修改、读回 | 24 | 2 分 32 秒 |
| 记忆写入与最终交付 | 6 | 28 秒 |

这里不是“写好了还瞎改”。例如，它把 Hermes 的“达到约 80% 就整理记忆”修正为“文档建议，不是程序强制规则”，还纠正了当前会话怎样读取新记忆的说法。这些修改有价值；另外也有删除内部英文名、替换措辞等小改动。

**这些轮次会花钱，是因为当时每次请求已带入二十多万 token 的上下文。** 补查一次、修改一处，再请求模型，都要带上所需历史。这 24 轮累计输入约 **585 万 token**，超过 PaperWiki 整个任务约 **265 万 token**。有价值的核对也有成本，不能把所有额外轮次都当成浪费。

### 8.4 PaperWiki 这次把事情安排得更集中

我们前 19 轮研究多个仓库，经常一次安排几项查找和读取；第 20、21 轮各提交两张卡片，随后收尾并回答。四张卡片没有另配四份证据文件，也没有保存后再花二十多轮补查修改。

这解释了为什么我们模型往返更少、交付更短，但也有取舍：关键事实抽查约 **80 分对 85 分**，一些默认路径和条件没有查全。更少的步骤，既可能来自更集中的安排，也可能来自少做了一部分有用工作。

**两边都能批量调用。** WorkBuddy 这次有 21 轮一次调用多个工具，首轮三个网页搜索也实际并发。还有一个需要如实说明的问题：PaperWiki 虽然有三个读工具线程，仓库工具内部却用同一把锁包住整个操作，仓库请求实际会排队。因此，不能把线程池或外层时间重叠当成仓库读取的并发优势。

### 8.5 费用差也能对上具体记录

按同一组历史价格，PaperWiki 约 **1.10 元**，WorkBuddy 约 **1.77 元**。约 **0.663 元**差距中，约 **0.622 元**来自缓存命中的输入项。

简单说：**重复传入的内容即使命中缓存，也仍然计费。** WorkBuddy 有更多轮次，尤其写完后的补查与小修改发生在历史已经很长时，所以累计输入更大。这是本次费用差的重要来源；不能解释成 WorkBuddy 不会用缓存，它的缓存命中率实际上更高。

本轮没有证据说明 PaperWiki 靠自动摘要压缩省下这些钱，也没有调用大结果回读工具，不能把这些已有能力算作这次提速的原因。最后一次七工具精简晚于本次实验，同样尚未计入收益。

### 面试时可以这样说

> 我没有只比较总耗时，而是把原始记录拆成模型等待、工具执行和写后修改。发现这次时间差主要在工具：WorkBuddy 顺序克隆四个仓库，再做了几次范围很宽的本地搜索；写完后又继续补证和修订。PaperWiki 的读取和保存安排更集中，因此本轮更快、更省，但也漏了一些信息。这让我能提出具体优化方向，而不是笼统说自己的框架比通用智能体先进。

完整阶段用量、慢命令编号、修改内容和仓库锁核对见 [逐轮分析报告](docs/audits/WORKBUDDY_TRACE_CAUSAL_ANALYSIS_2026-09-28.md)。这些记录能够解释本次开销去了哪里；若要确认哪项设计每次都能省钱，还需要同条件重跑。

## 9. 工具与 MCP 的边界

**工具**定义模型能做什么，包括名称、参数和返回值；**MCP** 是把这些能力提供给不同客户端的一种连接协议。一个 MCP 服务可以暴露多个工具，模型最终仍需要理解工具参数。

原 arXiv MCP 包装没有成为当前聊天主循环的必经路径。业务本来就在 Python 服务内部，再维护一个独立包装需要额外处理进程启动、配置、协议和测试。本次移除包装，保留论文服务，把四种动作合并成 `arxiv`。

| 情况 | 选择 |
|---|---|
| 只有 PaperWiki 内部使用论文搜索与入库 | 直接调用内部服务，再提供统一工具 |
| 希望多个独立客户端复用同一能力 | 可以增加 MCP 适配层，共享业务实现 |
| 要独立部署、由外部团队管理服务 | 评估 MCP 与鉴权、部署、版本兼容的配合 |
| 只想让工具列表少几个名字 | 不需要因此引入 MCP；调整工具接口即可 |

面试可这样说：

> 我们删除的是没有实际进入主链路的协议包装，没有删除论文检索与入库能力。工具定义业务动作，MCP 解决跨客户端连接问题；只有存在这个复用需求时，额外协议层才有明确价值。

详见 [工具与 MCP 边界案例](docs/design/TOOL_MCP_BOUNDARY_CASE.md)。

## 10. 安装、启动与测试

### 10.1 从源码运行

需要 Python 3.10 或以上、Node.js/npm；研究命令需对应的 PowerShell 或 Bash，仓库检出需 Git。

```powershell
git clone https://github.com/ouchfys/LLM-WIKI.git
cd LLM-WIKI
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e .
Copy-Item .env.example .env
```

编辑 `.env` 后启动：

```powershell
paperwiki web
```

启动器会按需安装前端依赖和构建页面，默认监听 `127.0.0.1:8000`。源代码留在安装目录，运行数据放到数据根目录。

| 配置 | 用途 |
|---|---|
| `DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL / DEEPSEEK_CHAT_MODEL` | 研究模型连接 |
| `PAPERWIKI_THINKING_EFFORT` | 默认思考档位：none、low、high、max；界面可覆盖 |
| `BAILIAN_API_KEY` | 可选语义向量服务；不使用时关闭向量检索配置 |
| `WIKI_VECTOR_SEARCH_ENABLED` | 是否使用语义检索，配合关键词检索与融合排序 |
| `MINERU_API_TOKEN` | PDF 精细解析服务凭据 |
| `GITHUB_TOKEN` | 可选 GitHub 访问凭据，提升认证访问可用性 |
| `PAPERWIKI_HOME` | 数据根目录 |
| `LLM_WIKI_API_URL` | 论文服务调用本地入库接口的地址 |

不把 `.env`、访问凭据或私人数据库提交到 Git。GitHub 凭据需由后端配置，其他客户端的登录状态不会自动传给 PaperWiki。配置凭据也不保证免于所有访问限制。

使用独立测试目录：

```powershell
$env:PAPERWIKI_HOME = "$env:USERPROFILE\Desktop\paper wiki测试"
paperwiki web
```

端口被占用时，确认原服务是否仍在运行；需要另开端口则同步修改入库接口地址：

```powershell
$env:LLM_WIKI_API_URL = "http://127.0.0.1:8001"
paperwiki web --port 8001
```
